# 第三阶段人物姿态图像编辑调研与显存预算

日期：2026年9月8日。依据：工作区《人物图像姿态编辑任务书_v3.docx》、用户提供的两段方案材料，以及本次核对的论文、官方仓库、模型配置与公开权重文件头。用户已明确：**6B限制针对生图主干；现有设备为RTX 6000D 84GB。**

## 后续补充 按Qwen Edit家族压缩模型收紧选型

用户随后强调任务书中的Qwen-Edit类要求，希望优先寻找由该家族蒸馏/压缩出的≤6B模型。因此，**前一轮以DeepGen为主路线的推荐暂不作为最终选型**。DeepGen/Klein采用Qwen编码器，并不能证明它们属于Qwen-Image-Edit的压缩学生模型。下文有关它们的核算保留为技术备选，48GB/80GB预算也仅适用于原先明确的训练配置。

2026年9月8日补查结论：**找到Qwen-Image的标称6B压缩研究，以及可下载的Qwen-Image-Edit剪枝版；尚未核实到同时满足“源自Qwen-Image-Edit、主干≤6B、已公开权重、具备编辑能力”的现成模型。**

| 工作 | 参数与蒸馏类型 | 编辑与发布证据 | 本项目结论 |
|---|---|---|---|
| [Amber-Image-6B](https://arxiv.org/abs/2602.17047) | Qwen-Image 20B→10B→标称6B；结合剪枝、双流/单流结构转换与知识蒸馏 | 作者明确定位为文生图；本次查作者HF组织及文件API，仅见README和两张SVG等4个文件，未见权重和推理代码 | 最接近参数压缩方向，但不能当现成Qwen-Edit 6B基座；严格参数量也尚不能复核 |
| [OPPO Qwen-Image-Edit-Pruning](https://huggingface.co/OPPOer/Qwen-Image-Edit-Pruning) | 删除20层、保留40层，作者报告13.6B；另有4步版本 | 有权重及QwenImageEditPipeline用法 | 血缘和编辑能力符合方向，参数超标；4步不会变成4B |

OPPO的[PPCL官方仓库](https://github.com/OPPO-Mente-Lab/Qwen-Image-Pruning)提供剪枝和蒸馏流程，公开文生图模型可到10B级；不能把文生图10B或编辑13.6B进一步口头折算成可用的6B编辑模型。

若上述条件都必须满足，合理的下一步是获得已有压缩学生的真实权重与编辑证据，再进行外挂训练验证。自行把Qwen-Image-Edit从20B蒸馏到≤6B会新增“训练学生主干、恢复编辑能力”的工作，超出原先“固定现有生成基座、只训练外挂”的实施范围，不能沿用此前外挂训练的显存和周期估计。离线教师数据可减少教师与学生同时驻留显存，但不能免除训练学生与质量验证。

使用与验证：本补充可用于更新项目选型讨论。当前不能直接测试Amber，因为所查公开仓库没有checkpoint。将来取得候选后，先核对主干去重参数量，再用源图＋编辑指令测试身份/服装保持，最后测外挂真实forward/backward/optimizer峰值。OPPO现成模型可作压缩编辑方法对照，但不可作为≤6B交付模型。本次未执行蒸馏或GPU训练。

## 前一轮宽口径方案与预算

**以下方案以“允许使用Qwen编码器的第三方编辑模型”为前提：采用冻结DeepGen编辑基座，只训练约100M～300M的结构控制器。硬件预算可按48GB级开展512像素原型，80/84GB级开展1024像素、batch size 1的完整实验。这里给的是选型预算，不是已经测出的峰值，也不是最低显存保证；不能转用于尚未选定的Qwen-Edit压缩学生。**

本次完成了公开checkpoint张量规模核算和关键代码检查，没有连接到用户的84GB训练设备、下载完整权重或执行真实训练。材料中的“512²需25～35GB、1024²需50～70GB”没有本项目实测依据，应撤下其确定性表述。是否低于24GB、48GB是否能训练1024²，都需要固定控制器与训练配置后测量。

## 任务边界与路线选择

项目的三个技术环节是人体解析、动作重定向、图像编辑；任务书的合同进度则分两个阶段，两者不要混淆。第三环节接收第二环节的目标人体结构，不重复开发重定向算法。前两环节目前是团队分工，不能据两段材料的措辞认定它们已经完成。

第三环节的输入建议固定为：源人物照片、目标SMPL-X、相机与投影信息、稳定的人物A/B对应、接触关系，以及可选文字指令。输出是保留人物身份、服饰和场景的目标姿态图像。仅有SMPL-X参数而缺少相机、尺度、人物对应，不能确保控制图与原图对齐。

任务书还要求与Qwen-Edit基线比较交互图像主观质量及手部细节，均提出“高于5%”的要求。应在实验前固定基线版本、输入信息、盲评规则和“5%”的计算口径；不自行把这一句解释成55%胜率或5个百分点。较小基座在通用编辑榜单上的成绩不能证明已经达到项目验收指标。

## 显存到底花在哪里

对于“冻结基座＋训练外挂”，峰值可拆为：

`峰值 ≈ GPU上常驻的冻结权重 + 外挂训练状态 + 反向所需激活 + 临时工作区及运行时开销`

冻结参数能省去该部分的参数梯度和优化器状态，但控制器输出必须经过生成主干才能影响损失，梯度需要穿过主干返回控制器。因此不能对整个DiT调用套上no_grad，也不能直接把带no_grad装饰器的推理pipeline当训练函数。[PyTorch自动求导说明](https://docs.pytorch.org/docs/main/notes/autograd.html)

### 可精确核算的部分

DeepGen的组件为：DiT 2.4697B、VLM 3.7546B、connector 0.43245B、VAE 0.08382B。connector公开权重按FP32存储，其余上述权重按BF16存储；pipeline加载代码会按指定dtype转换connector。因此**14.35GB左右的权重文件数据、13.48GB的BF16等效权重、12.56GiB的BF16等效权重**是不同口径，不能混用。B表示十亿个元素，GB按10⁹字节，GiB按2³⁰字节。

若冻结的VLM、connector、VAE结果提前缓存，训练阶段只常驻DiT，则冻结权重约为**4.60GiB**。缓存预处理本身仍需要加载编码模块，但可以分阶段执行，不必与训练峰值叠加。这里假设外挂仅接入DiT，不接入VLM或connector。

外挂训练状态可用16字节/参数做保守预算，例如FP32参数、FP32梯度和Adam两个FP32状态；或者有FP32主副本的混合精度实现。纯BF16参数与不同优化器的占用可能更低，临时优化器开销另计。

| 外挂参数量 | 以16字节/参数计算的状态预算 |
|---:|---:|
| 100M | 1.49 GiB |
| 200M | 2.98 GiB |
| 300M | 4.47 GiB |
| 600M | 8.94 GiB |
| 1B | 14.90 GiB |

因此，DeepGen全组件常驻＋300M外挂的上述静态部分约**17.03GiB**；缓存编码结果＋300M外挂时约**9.07GiB**。这两个数均尚未包含激活、控制图、输入缓存、CUDA工作区和预览推理，不能当作最低卡容量。

### 决定峰值的部分尚须实测

DeepGen实际编辑forward会把目标噪声图和参考图的latent token拼接。按VAE缩小8倍、patch size 2估算，一张1024²图约4096个图像token，源图和目标图共约8192个，另有文本/连接器token。其config为24层、隐藏宽度1536，并含额外注意力层。[Transformer配置](https://huggingface.co/deepgenteam/DeepGen-1.0-diffusers/blob/main/transformer/config.json)、[实际编辑forward代码](https://huggingface.co/deepgenteam/DeepGen-1.0-diffusers/blob/main/deepgen_pipeline.py)

这解释了为什么用纯文生图显存推算编辑会低估。全分辨率参考图数量、控制token数量、注入层数、attention实现、checkpointing、batch和额外可微损失都会改变峰值。双人本身不自动使显存翻倍；如果仍是一张场景图、相同分辨率与token数，主要变化是控制通道和任务难度。

本项目不需要将完整50步采样链展开反传。MVP沿用基座的单随机时间步flow/diffusion训练目标；生成几十步的图像留到验证阶段。额外加入可微人脸、姿态重建或多步采样损失后，必须重新核算。

### 面向现有84GB卡的资源决定

以下是工程资源档位建议，**不是已测峰值范围**。限定：单源图、单目标图、每卡batch 1、BF16、DiT和外挂均做适当activation checkpointing、高效attention、100M～300M外挂、无多步采样反传；必要时缓存编码结果。

| 卡容量档位 | 本项目建议用途 | 判断强度 |
|---|---|---|
| 24GB | 512²、较小外挂、充分缓存/卸载的低显存探索 | 可能可行，不能承诺，不设为交付最低配置 |
| 48GB | DeepGen的512²原型和逐步增加控制条件；再实测768² | 合理开发预算，不是保证所有配置都能跑 |
| 80/84GB | 逐步开展1024²、双人场景和完整控制条件实验 | **推荐现有设备直接开工**；具体峰值仍待测 |
| 多卡 | 更多吞吐、更大batch，或单卡实测确实不够时 | 当前没有必须先申请多卡的依据 |

普通DDP会在每卡复制模型，2×48GB不等于一张96GB卡。只有正确的参数/优化器/激活分片才可能解决单卡容量问题，并会引入通信和适配成本。

可用于项目沟通的表述：**“第三阶段不做生成主干全参数微调，拟冻结≤6B生图主干，只训练轻量结构控制模块。计划使用单张84GB显卡开展研发，48GB级作为512分辨率原型预算，80GB级作为1024分辨率完整实验预算。最终最低显存以固定配置的完整训练步峰值及验证峰值为准。”**

## 可以直接复用的代码和仍需适配的地方

首选结构为：

```text
源照片和指令 → 冻结Qwen视觉编码与connector → 固定语义条件
源照片 → 冻结VAE → 参考latent
目标SMPL-X和相机 → Pose / Depth / Part与Person-ID / Contact
                                  ↓
                       一个轻量多条件控制器
                                  ↓ 多层残差
                    冻结DeepGen编辑DiT → 编辑图像
```

**复用DeepGen编辑路径，借用Diffusers训练循环和ControlNet接口。** DeepGen公开pipeline的transformer已接收block_controlnet_hidden_states并进行逐层残差相加；因此不必从零开发注入机制。仍需让残差对齐“目标token＋参考token”的序列，可先只控制目标段，对参考段补零；保留原有attention mask与图像布局。这是接口检查得出的实现建议，还未完成训练验证。[DeepGen pipeline](https://huggingface.co/deepgenteam/DeepGen-1.0-diffusers/blob/main/deepgen_pipeline.py)

Diffusers的train_controlnet_sd3.py可以借用优化器、flow时间步采样、分布式训练和保存逻辑；其中原始CLIP/T5编码、数据字段、预览pipeline必须改成DeepGen的真实编辑条件。DeepGen自己的默认SFT也会训练DiT/VLM相关模块，不能原样启动后声称符合“全部冻结”。[Diffusers SD3训练脚本](https://github.com/huggingface/diffusers/blob/main/examples/controlnet/train_controlnet_sd3.py)、[DeepGen训练说明](https://github.com/deepgenteam/deepgen/blob/main/TRAIN.md)

默认复制大量DiT块的SD3ControlNet不自动等于100M～300M。应显式选择浅层或窄层控制分支，统计实际trainable numel，再决定是否达到轻量目标。100M～300M是设计预算，尚无证据证明该容量一定足以处理所有双人交互。

建议多种控制图沿通道融合进入同一个编码器，共享投影层；不要为Pose、Depth、Normal、Part、Contact各复制一套控制网络。DiT不具备U-Net那样天然的空间金字塔，不能照搬“1/8、1/16、1/32多尺度特征分别接不同分辨率层”的假设；应明确每层输出如何映射到同一token网格。

这套技术栈复用现有模型和训练算法，研究工作集中在目标结构表达、残差对齐、身份归属及接触条件上。没有查到一个能够直接下载、同时满足“冻结≤6B Qwen相关主干＋SMPL-X双人接触编辑”的完整现成checkpoint。

## 数据集应按监督类型选择

监督样本应为：`同一人物或同一对人物的源图 I_s + 目标结构 C_t + 真实目标图 I_t`。前两环节产生的任意重定向结果通常没有对应真实目标图，因此不能自动变成第三阶段的监督训练数据。训练时可从已有视频取同身份、同服装、同机位的不同姿态帧；推理时再输入第二阶段的新重定向姿态。

| 数据 | 已有资源与合适用途 | 需要补齐或限制 |
|---|---|---|
| [DeepFashion及CFLD配对流程](https://github.com/YanzuoLu/CFLD) | 单人人物跨姿态配对、关键点、成熟预处理；适合Pose-only起步 | 不自带准确SMPL-X和双人接触；服装检索配对仍需核验身份、衣着与背景，不能默认都满足严格保留任务 |

## 控制表示与训练安排

第一版只做Pose＋Depth，并保留人物A/B对应；双人阶段尽早加入Person-ID。Normal、部位与Contact逐项增加。SMPL-X裸身体表不等于衣服外表面，应把几何作为结构约束，避免把宽松衣服硬贴到裸体网格上。

Contact建议同时保存两种表示：一是`A右手↔B左手`之类的部位/顶点对应关系，二是投影到图上的接触热图与可见性。单张无身份的二值接触图不足以表达“谁与谁接触”，也不能表达全部被遮挡的三维接触。全局关系可编码为少量条件token；空间热图进入共享控制器。这是本项目需验证的设计，而不是某个现成权重已经保证支持的功能。

损失先使用基座flow matching目标：目标图编码为latent，抽随机时间步并加噪，控制器根据目标结构输出残差，冻结DiT预测该时间步目标，只对外挂更新。具体σ采样、缩放、预条件与预测目标沿用所选checkpoint的训练实现，不能混用SD1.5的噪声调度。[SD3训练实现](https://github.com/huggingface/diffusers/blob/main/examples/controlnet/train_controlnet_sd3.py)

建议的实验推进为：

1. 用16～32组干净配对验证能否小样本过拟合，确认外挂有非零梯度，主干未更新，目标姿态会随条件改变。样本数是调试建议，不是论文配方。
2. 扩到单人Pose/Depth，再加入同一对人物的交互数据；先解决A/B身份交换、遮挡与尺度对齐。
3. 增加部位、Normal、Contact；固定训练数据、步数和参数预算做消融。需要时对控制条件随机dropout，避免某一条件缺失就失效。
4. 再评估是否确需外观支路、手部区域加权或局部二次编辑。不要一开始就把身份网络、可微SMPL-X重建器和多步采样都放入训练图。

冻结Qwen、connector和VAE后，源图语义、参考latent及目标latent可缓存。缓存应绑定图像裁剪/尺寸、prompt、编码器版本；随机裁剪或更换prompt后不能继续使用不匹配的旧缓存。目标噪声与时间步仍在线随机生成。

编辑mask应覆盖原人物与目标人物投影的并集并适当膨胀。mask外合成原图有助于保护背景，但人物移开后新露出的区域仍需生成，阴影与边界也需要处理，不能宣称alpha blend已经解决所有背景保持问题。

## 在84GB卡上怎样得到可提交的真实数字

不必等待完整数据集和完整contact算法完成。具备真实forward、真实外挂和一组尺寸正确的训练样本后，就能测容量；显存测量可用合成数值控制图，但模型应加载真实权重。随机权重或缩小层数的实验不能当最终容量结果。

第一轮固定DeepGen、100M～300M以内外挂、BF16、batch 1、一个源图、一个目标图、高效attention和checkpointing。分别测试512²、768²、1024²；各分辨率用独立进程，避免前一个大尺寸的缓存污染比较。编码在线与编码缓存两种配置分别测。

每个配置至少记录：

| 记录阶段 | 必须包含的操作 |
|---|---|
| 加载峰值 | 模型加载、dtype转换、设备移动，确认没有同时保留重复pipeline |
| 冷启动训练峰值 | 第一次forward、backward、optimizer.step，覆盖Adam状态初始化 |
| 稳态训练峰值 | 预热后10～20个完整更新步，覆盖实际梯度累积配置 |
| 验证峰值 | 实际生成预览图，覆盖CFG与计划使用的参考图数量 |

在实际训练循环里调用torch.cuda.synchronize后读取max_memory_allocated与max_memory_reserved，同时用nvidia-smi监控设备总占用。allocated不包含所有CUDA开销，reserved也不等于进程之外的占用，因此三者一起报。下面是**需要嵌入真实训练程序的测量示意，不是现成训练器**：

```python
import torch

def measure(label, operation):
    torch.cuda.synchronize()
    torch.cuda.reset_peak_memory_stats()
    operation()  # 必须包含本阶段的所有实际操作
    torch.cuda.synchronize()
    print(label, {
        "allocated_GiB": torch.cuda.max_memory_allocated() / 2**30,
        "reserved_GiB": torch.cuda.max_memory_reserved() / 2**30,
    })

# 模型已经正确构建，优化器状态尚未初始化。
# one_update必须执行真实forward、backward、optimizer.step和zero_grad，
# 不返回或积累带计算图的Tensor；若使用梯度累积，执行一个完整累积周期。
measure("first_update", one_update)
for _ in range(3):
    one_update()

def steady_updates():
    for _ in range(20):
        one_update()

measure("steady_training", steady_updates)
measure("validation", run_real_validation)
```

还需确认梯度链是真的：基座参数requires_grad=False且不在optimizer里；经过首几步后外挂关键层grad有限且非零；基座训练前后参数哈希一致。零初始化残差层可能导致最初一步更早的控制编码层梯度为零，应跨数步检查。关闭外挂时应恢复相同基座的结果，不能为了降低显存误断梯度而“空训练”。

输出结果应同时附上GPU实际识别型号、可用总容量、驱动/PyTorch版本、模型revision、trainable numel、分辨率、参考图数量、batch、梯度累积、attention后端、checkpointing和缓存开关。把加载/训练/验证的最高设备占用作为容量判断依据，额外保留约10%～15%工程余量；不要把某次低峰值直接写成所有场景都适用的最低配置。
