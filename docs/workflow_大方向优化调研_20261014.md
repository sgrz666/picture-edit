## 2. P0 把已验证的 A 实测定标接进生产（解耦的一阶）

**问题**：输入骨架同时携带动作、尺度、位置，而流程用 B 的检测框决定 A 的人身大小。
近景/截断人物最严重；`torso_ratio.py` 已量出单人线 8 张源帧的躯干/框高从 0.259 跨到 0.524，
所以 0.31 这个常数在单人口径**根本没有取值可言**（双人线中位 0.285 才勉强成立）。

**已有证据**：`diagnostics/2026-10-13-scale-generation/` 的 6 张真实生成图，
提示词与采样全部逐字节冻结、只改骨架，近景三例的"生成/A 躯干比"从 0.5 量级抬到 0.95 量级，
并且 head 投影高度同步回到 A。这已经是**做过的实验**，只差搬进生产路径。

**方案**（按 AGENTS.md 2.3，跨实验可复用的部分提升到仓级）：
1. 把 `geometry_ablation.py` 的定标式（两边统一取"肩中点→髋中点"、以 A 髋中点锚定、画外骨段只裁不挪）
   提为 `--framing source_measured`，成为新的默认；`source_person`/`source_torso` 保留为可复现旧数字的显式档。
2. A 侧肩/髋四个锚点任一置信度 <0.3 → 退回上一档并在 `geometry/stage.json` 写 `framing_fallback` 原因，不静默。
3. 门禁直接复用双人线的 `size_compliance.py`（逐人 实测躯干 ÷ 请求躯干）与 `scorecard.py` 的 `torsoG`；
   读数目标不是 PCK，而是 torsoG→1.0。当前 `wp1_accept_hard02` 的 torsoG 是 0.815。

**必须知道的约束**：`src/pose_edit/geometry.py` 在缓存指纹的 CODE 列表里，改它会让**所有**既有 run
报 `workflow code changed`，并连带作废正在跑的 85 格矩阵的 PE/生成缓存。
`docs/workflow_multiple_设计_20261013.md` 已经把这条明确排在批量之后。**不要提前动。**
批量期间的替代路径：在 `workflow/diagnostics/` 里继续用独立脚本验证（`geometry_ablation.py` 就是这个用途），
或把新逻辑写成独立模块、等批量收尾一次性接线。

**文献/社区**：逐骨段改写比"全局统一缩放"更贴近人体表观，
见 [PINet：Adaptive Hierarchical Deformation](http://cic.tju.edu.cn/faculty/likun/projects/PoseTrans_pg/assets/PINet.pdf)
与 [Normalized Human Pose Features（ICCV 2021，把姿态映到预定义 3D 骨架以解耦动作与体型）](https://cqf.x10host.com/papers/Normalized_Human_Pose_Features_ICCV2021.pdf)；
参考姿态与人物不对齐是当前公认未解问题，见
[One-to-All Animation（alignment-free，2025）](https://arxiv.org/html/2511.22940v3)。

## 3. P1 真解耦：以 A 的形体为模板重定向 + 合同那条 80% 指标

**为什么 P0 不够**：P0 只改统一缩放与锚点，B 的骨段比例原样保留（诊断报告约束 1、4 明说）。
合同要的是"身高高低、体型胖瘦"由 A 决定、动作由 B 决定——这是**逐骨段**的问题，不是全局缩放问题。
实测侧的证据同向：`scorecard.py` 的 `shape`（姿态不变的骨长比最大相对漂移）在唯一 `ok` 那一行是 0.612，
量级远超背景保持类指标的正常噪声，说明当前管线确实在改人的体型。

**两档实现，先做便宜的那档**：
- **P1a 2D 逐骨段改写（CPU，无需新估计）**：用已有 DWPose-134 槽位表测 A 与骨架各自的骨段长
  （肩/肘/腕、髋/膝/踝、骨盆→颈、颈→头），把 B 骨架每段按 A 的段长逐级重挂（自骨盆向外，保相对角度），
  再整体按 P0 锚定。A 侧关键点走仓库里现成的 DWPose ONNX（CPU），不需要 SMPLest-X 跑 A。
- **P1b 参数化重定向（真三维）**：`smplx_worker.py` 扩成 A、B 各估一次，取 A 的 β/骨长/相机距离与 B 的姿态旋转，
  在 SMPL-X 模板上合成后投影回 A 画布。代价是多一次 GPU 估计，收益是体型与透视都跟着 A。
  参考：[SMPL-X 模型定义](https://smpl-x.is.tue.mpg.de/)、
  [Disentangled Self-Driven Human Pose Transfer（含逐部件 shape consistency 指标）](https://arxiv.org/html/2210.01887v3)、
  [Unsupervised Shape and Pose Disentanglement for 3D Morphable Models](https://virtualhumans.mpi-inf.mpg.de/papers/kzhou20unsupervised/paper.pdf)、
  估计器本身见 [SMPLest-X](https://arxiv.org/html/2501.09782v1)。

**先补指标，否则改了也无法验收**。合同口径"人物身高的高低、体型的胖瘦**相对估计**准确率 ≥80%"落地为：
1. 量：身高代理 = 髋→踝 + 踝→头顶（回估关键点骨长和）；体型代理 = SMPL-X `β[0:2]` 与肩宽/髋宽、腿长比。
2. 判：同一对里 A 与输出（双人场景再叠 A 内两人之间）比高低、比胖瘦，输出三分类（更高/相近/更矮）。
3. 校准：拿"伪 GT"当真值——iPER `baseline_50_eval_pairs.jsonl` 的真 target 帧与 A 之间做同样判定，
   准确率 = 管线判定与真值判定一致的比例。这就是无GT调研里第四类参照，只差把它变成一条**数字口径**。
4. 落点：`src/evaluation/shape_height_metrics.py`（与 `no_gt_metrics.py` 同族，只读已有产物），
   `evaluate2.py` 增一列，`scorecard.py` 增 `heightAcc`/`buildAcc` 两列。

## 4. P2 控制信号表示消融（目标一的验收主体，今天 0 覆盖）

**这是合同白纸黑字、却最没动的方向**：目标一要"研究分析参数化模型、法向图、接触图等多种控制信号的有效性"。
仓库里 `ControlSignalGenerator` 已经能出骨架 / 点云+深度+法向 / 双人接触图，
训练侧还有 nvdiffrast 法向图渲染链（`add/tools/SMPLest-X/scripts/render_iper_v1_normals_nvdiffrast_exact.py`、
`prerender_iper_v4_cache.py`）——原料齐了，缺的是**接进 workflow 并对照**。

**方案**：`run.py` 加 `--condition`，一次实验四臂，其余变量逐字节冻结（沿用 scale-generation 那套
"冻结 A / 提示词 / seed / 采样，只换条件图"的协议，它的可行性已被 6 张图验证）：
- `skeleton`：现行基线；
- `normal`：A 视角下 B 的 SMPL-X 法向图（或源-目标混合）；
- `dense_mix`：骨架 + 半透明法向/深度叠加（避免基座从没见过该分布而全盘崩溃）；
- `none`：**只给文本不给任何姿态条件**——这条同时是合同要求的"Qwen-Edit 基线"，见 P4。

判据用 `scorecard.py` 三主指标（`pckDW*`、`torsoG`、`idcos`/`bgMAE`）+ P4 的主观成对。
7 对 × 4 臂 × 3 seed = 84 次生成；按双人线实测（768/30 步 一次 86–142 s、峰值 34 GiB），
单人是它的十分之一量级，但要过 `gpu_gate.sh`。

**文献取向值得注意**：[DisPose（ICLR 2025）](https://arxiv.org/abs/2412.09349) 的结论反而是
**不必上密集输入**——它从稀疏骨架里解耦 motion field 与关键点对应，并用 Joint Reliability Augmentation
丢弃不可靠点，就拿到了更好的可控性。也就是说"法向图一定比骨架好吗"是个真问题，不是前提；
这正好是要做消融的理由。条件置信度加权的思路见
[ControlNet++（ECCV 2024）](https://arxiv.org/html/2404.07987v1)；
把姿态信号编进文本嵌入的隐式路线见
[PoseAnimate 的 Pose-Aware Control Module](https://arxiv.org/html/2404.13680v3)。

## 5. P3 手部与接触：合同点名的两个失败模式

现状：hand 组是全部指标里最差的一组（README 表 0.055–0.359，body 组是 0.033–0.076）；
手指畸形没有任何检测；`scale-generation` 那轮实拍到"三只手"的失败图（hard_02 原提示词与新骨架冲突）。
合同阶段二的验收写得非常具体：**手部无明显结构性错误**、握手/牵手/搭肩的**手部细节合理主观优胜率 +5%**。

**四项可独立落地的改动**：
0. **先承认量不出来**（2026-10-14 实测，`src/evaluation/hand_plausibility.py --all --distribution`）：
   现有 13 个 run 的 50 只手，掌长 p5/p50/p95 = **17.5 / 39.5 / 63.9 px**，
   **46/50（92%）低于 60 px 的可判读下限**。768 分辨率下掌长 40 px，检测器几像素的误差就等于
   一整节指骨，所以"精确到手指""手部无明显结构性错误""手部细节优胜率"这三条合同要求
   **在当前管线尺寸上没有评测意义**——不是指标不好，是根本量不到。
   同一次实测顺手否掉两条我本来要写的检查：指骨**径向单调性**（弯手指的指尖本来就更靠近手腕，
   真实 guide 数组里就有 `middle [1.07,1.39,1.41,1.38]`）与**逐节长度比**（合法手的 p1–p99 已跨 0.05–0.69，
   曲率与透视前缩主导）。留下的检查只有站得住的三条：指尖融合（手套手）、
   指长越界（>3.2 倍掌长）、以及"测不了就排除"。唯一够大的那只手（`tt_00304_0147_0405`）
   立刻判出 `inspect`：**左右手各有两根指尖融合**。
   **结论：手指这一层要先把区域放大**——要么提分辨率，要么走手区 crop 的条件与评测两用时。
1. **手区条件加权**：手部 42 点单独加粗/放大绘制，或把手区 21 点单独渲染一张高分辨率小图作为第三条件。
   零训练成本，先量它对各臂 PCK(hand) 的影响。区域增强路线见
   [Robust Photo-Realistic Hand Gesture Generation](https://arxiv.org/html/2505.10576v2)，
   两手联合建模见 [HandDiffuse](https://arxiv.org/html/2312.04867v1)。
2. **手指合法性指标**：已落地为 `src/evaluation/hand_plausibility.py`（只读 `evaluate.py` 已有的
   `final_keypoints.npz`，零新增推理、零 GPU）。三条检查按上面第 0 条的实测取舍收敛到
   指尖融合 / 指长越界 / 测不了即排除，`compare()` 只记"guide 没有、生成图才有"的新旗标，
   不把向导本身的毛病算给生成器。**没有**接进 `evaluate2.py`：`no_gt_metrics.py` 在
   `evaluate2.py:44` 的 CODE 指纹里，动它会让已打分的 run 全部重算，排在批量之后。
   顺带更正一处认知：`hand_anomaly` 这个字段在 `no_gt_metrics.py` 里**并不存在**
   （`grep -n "hand\|finger"` 于 `evaluate2.py` 与 `no_gt_metrics.py` 均无命中），
   无GT调研 §轴4 把它列成"待补"，本模块补的就是它。
3. **接触合理性**：把 `compute_two_person_contacts` 的接触图同时用作条件和评测证据——
   请求接触区 vs 生成图回估接触区（Hi4D 有 instance mesh，可算测地接触），
   对合同的"遮挡、穿模、接触错位"逐条给数。数据集侧参照
   [Hi4D](https://arxiv.org/abs/2303.15380)（4D 双人扫描、逐实例网格）与
   [Harmony4D（in-the-wild 双人视频）](https://arxiv.org/html/2410.20294v1)。
4. **多人扰动与身份—姿态绑定**：`--subject largest` 之后画面里其他人会不会被改，现在没人测。
   `no_gt_metrics.py` 已预留 `nonsubject_*`；实例级身份—姿态绑定失败的近期做法见
   [AnyCrowd](https://arxiv.org/html/2603.15415v1)。

## 6. P4 主观评测基础设施与缺失的基线臂（交付风险最高）

合同三条验收挂在主观读数上（≥90% 合理、+5% 优胜率），而仓库里**一条主观协议都没有**。
更硬的一点：**"+5% vs Qwen-Edit 基线"目前没有基线可减**——workflow 的每一次生成都给了骨架图，
纯文本编辑的臂从未跑过。这条不补，阶段二验收无法自证。

**建议一次建齐（纯 CPU + 前端，不动任何指纹，现在就能做）**：
- `workflow/human_eval/protocol.md`：轴（身份可辨 / 动作准确 / 交互自然 / 手部结构 / 整体）、
  5 档 Likert + **强制成对选择**（win/lose/tie）、标注者 ≥3、随机左右、隐藏臂名、
  一致性用 Fleiss κ，优胜率 =(win−lose)/n 配 bootstrap CI95。
  `--condition none` 臂作为每对的对照，`size_compliance` 与 `joints_excluded_ratio` 不达标者进"必审队列"。
- `workflow/human_eval/annotate.html` + `tally.py`：单文件离线标注页（键盘 1–5 / ←→），
  导出 jsonl；`tally.py` 出分轴表与 CI。样本量要按 +5% 反推，不是按"有几张图"正推：
  检出 5% 优势需要数百判定量级，因此单人测试集 7 对不够，**扩到 20–30 对**
  （iPER/TikTok/Hi4D 里可组，数据侧顺带完成合同"姿态类别覆盖"的字段要求）。
- MLLM 预筛只用来缩小送人工的子集，不作结论：本地 `Qwen-Image-2.1/text_encoder` 实测是带 `vision_config` 的
  Qwen3VL（无GT调研 §轴5 已验证），可离线复刻
  [VIEScore](https://arxiv.org/abs/2312.14867) 的 SE/OQ/D 与
  [Emu Edit 的识别式指标](https://arxiv.org/abs/2311.10089)；
  self-preference 与手部/计数盲区决定了它不能单独充当验收。

## 7. P5 隐式注入臂：合同写了、仓库有货、一次没跑

`config.json` 写死 `adapter:false / lora:false`，`generate_worker.py` 拒绝 peft 配置——这是基线该有的样子，
但目标三的原话是"**显式和隐式**控制信号注入"。仓库侧现成资产：iper_v6 单人长程 adapter、
BFH(Body+Face+Hand) 联合控制训练与评测（commit `4fc7457`）、Qwen 2.1 双 adapter 设计（`b0e6bc0`、`72e418e`）。
