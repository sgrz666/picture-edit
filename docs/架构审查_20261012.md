## 二、P0 — 阻断面

**P0-1 三处 git 状态互相分叉，没有可信主干。**
sg 的 main 指向 `3236657`，其本地 `origin/main` 引用停在 `8e01dbc`；Windows 工作副本 main 是 `72e418e`（记录为 ahead 5）；两侧 remote 同为 `github.com/sgrz666/picture-edit`。在 sg 上 `git ls-remote origin` 直接超时（该主机无外网），即 sg 侧提交推不出去；Windows 侧靠 `remote_node01`、`server-main`、`backup/current-work-20260926` 这类临时分支搬运历史。结果是"哪个提交是当前真本"不可判定，README 与目录文档描述的结构也可能已与工作区脱节。

**P0-2 测试套件在 sg 上无法整体运行。**
用 README 推荐的 qwen21 环境执行 `pytest`，收集阶段即 `Interrupted: 7 errors`：`tests/test_v66_hand_core.py` 等用例导入 `scripts.precompute_iper_face_features_v65`、`scripts.precompute_iper_hand_features_v66`、`scripts.audit_qwen21_weight_compatibility`，而这三个脚本此刻正处于"工作区已删除、删除未提交"状态。手工排除这 7 个文件后实跑结果为 573 passed / 30 failed；30 个失败全部来自同一句 `ModuleNotFoundError: No module named 'tests.test_deepgen_control_interface_v1'`——该文件在磁盘上存在，但仓库根无 `conftest.py`、`tests/` 无 `__init__.py`、也无 `pyproject.toml`/`setup.py`，因此以 `tests.xxx` 模块路径跨测试文件复用助手不成立。README 第 4 节把 `pytest tests/test_qwen21_*.py -v` 写成标准验收动作，按现状执行不出真实结论。

**P0-3 GPU 监控链路已断。**
`nvidia-smi` 返回 `Failed to initialize NVML: Driver/library version mismatch`（NVML 580.178），而 torch 2.8.0+cu128 仍报告 `cuda.is_available() True`、device_count 1。用户态 NVML 与内核驱动版本不匹配，说明驱动升级后未重启或包版本错位；依赖 NVML 的显存测绘（`vram_lab/`）与监控已失效。本次审查未做前向计算，故不能断言训练/推理一定失败，但一定无人能确认。

## 三、P1 — 结构性

**P1-1 `pose_control/v6` 与 `pose_control/qwen21_full` 是字节级复制的 fork。**
`diff -rq` 显示 v6 的 47 个 .py 与 qwen21_full 中同名文件全部逐字节相同（deepgen_adapter 612 行、control_core 512 行、checkpoint 399 行、condition_injector 305 行等成对一致），qwen21_full 只是额外新增 9 个文件（`qwen_adapter.py`、`qwen_runtime.py`、`execution.py`、`joint_training.py`、`data_runtime.py`、face 三件套、`frozen_bfs_lora.py`）；差异只出现在 README/目录说明。三条演进线同时是活的：`src.pose_control.v6` 被导入 84 处、`qwen21_full` 77 处、`qwen21` 40 处。任何控制注入层的修复都要在两份完全相同的代码里各改一遍，"尚未漂移"只是因为还没人改。

**P1-2 入口层迁移停在半路，且 README 推荐命令指向未入库的文件。**
根目录 25 个 `train_*/eval_*/run_*` 与 `scripts/` 下同名文件逐字节相同（`bfs_explore.py` 只存在于根目录）。git 跟踪的恰恰是根目录那一份，"整理后"的 scripts/ 150 个 .py 只有 16 个入库，而 README 第 4 节命令矩阵全部写成 `python3 scripts/train/...`、`python3 scripts/eval/...`。按文档执行依赖的是没有版本控制的副本；`scripts/` 里的改动也不进 git。

**P1-3 当前主力的 `workflow/` 子系统零版本控制。**
75 个 .py、81M，git 跟踪条目 0；`workflow/runs/` 下有 9 份 estimator 运行快照，每份都自带同一套 `inference.py`（347 行）/`base.py`（234 行）副本，快照与代码混在同一目录树。`workflow/config.json`（含 5 个绝对路径与两个解释器选择：几何走 `add/envs/smplestx_bw`，生成走 `~/nihaochen/envs/qwen21`）与 `configs/asset_registry.json`（README 第 3.6 节称为路径资产登记）均未入库。`workflow/.gitignore` 只覆盖其自身内部条目。

**P1-4 代码根同时充当环境根、数据根与产物根。**
`add/envs/` 有 4 个 7.6–8.1G 的 conda 环境（合计 62G 目录、6 万多个 .py 全是 site-packages），加上 `add/tools/` 9.9G、`add/outputs/` 14G；`experiments/` 63G、`datasets/` 46G、`models/` 19G。`.gitignore` 挡住了提交，但没挡住物理位置：任何全仓遍历都要穿过上百 GB 与十几万文件（生成目录文档的 `scripts/gen_folder_docs.py` 首当其冲），根分区 96% 占用使 checkpoint 与数据集写入没有安全余量。

**P1-5 忽略规则与历史跟踪相互矛盾。**
`.gitignore` 声明 `/results/`、`/data/*`、`/experiments/*`、`/deepgen/*`、`/model-qwen-edit/` 忽略，但 `git ls-files` 显示 results 下 2,580 个条目、demooutput 下 28 项仍在跟踪（`demooutput` 是指向 `results/legacy_demo_202609` 的符号链接）。已跟踪 + 已忽略 = 这些文件永远处于"一动就脏"的状态，而清理它们又会堆出 P0-1 里那种几十条待提交删除。

## 四、P2 — 摩擦面

- **无打包、靠路径注入**：没有 `pyproject.toml`/`setup.py`，229 个 .py 用 `sys.path.insert/append` 自行挂载仓库根；所有入口只能从仓库根以脚本方式启动，换机或换目录即断。
- **配置三处并存**：argparse 默认值内嵌绝对路径、`configs/*.json`、`workflow/config.json`，没有统一加载层。仅 src/scripts/workflow 与根脚本中，`/home/shangguanrz/project/pic-edit` 字面量出现 28 次、`/data/shangguanrz/pic-edit-datasets/TikTokData` 18 次。
- **库边界泄漏**：49 个 src 之外的脚本自行定义 `nn.Module`/adapter 或直接改 pipeline，`src/` 作为"核心库"的边界不成立。
- **文档体系强但与实况错位**：README（30K）、`目录总览.md`（24K）加每目录自动生成的 `目录说明.md`，覆盖度和可读性高于多数研究代码库；问题是它描述"应当如此"的结构（scripts/ 已分类、configs/ 有资产登记、tests 全绿），而非 git 与工作区实况，读者会据此做出错误决策。

## 六、建议处置顺序

1. **恢复可验证基线**：被删的 3 个 precompute/audit 脚本与对应的 7 个测试文件二者取其一（补回或连用例一起归档删除）；给 `tests/` 加 `__init__.py`，或把跨文件助手抽成 `tests/_helpers.py` 并显式导入，使 `pytest tests/` 一次给出可信通过数；对齐 nvidia 驱动/内核版本（多数是升级后未重启）。
2. **建立单一主干同步通道**：在 Windows 侧用 `git bundle` 把 sg 的 main 取回对账，之后统一"sg 提交 → bundle → Windows → push GitHub"；把当前 60 删除 / 15 修改 / 291 未跟踪收敛成一次有信息的提交，并清掉临时分支。
3. **让文档与 git 实况一致**：确定 `scripts/` 为唯一入口层并全部入库，删除根目录重复副本（如需兼容只留薄壳转发脚本）；`workflow/` 源码与 `configs/asset_registry.json`、`workflow/config.json` 入库，`workflow/runs/` 与产物快照改为忽略。
4. **收敛 fork**：把 v6 与 qwen21_full 的相同内核抽成单一包（如 `pose_control/core` + 各线 `adapters/` 差异层），三条演进线标注状态（活跃 / 冻结 / 废弃），废弃线移入 `archive/` 而不是留在 `src/`。
5. **结构性解耦**：环境迁出仓库目录（`~/miniconda3/envs` 或 `~/nihaochen/envs`），数据与权重统一留在 `/data/shangguanrz/` 以软链接入仓（现已部分如此，需去掉 `add/envs`、`add/outputs` 这类例外）；引入 `pyproject.toml` 做 editable 安装以消灭 `sys.path` hack；配置集中到单一入口。
