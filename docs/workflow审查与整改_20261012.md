## 一、发现的问题

| 编号 | 问题 | 实测证据 |
|---|---|---|
| W1 | 手工改 prompt 与"内容哈希即真理"的缓存契约互撞：常规重跑会静默重算 PE 并覆盖手写实验输入，而 `runs/` 不入 git，无任何副本 | `runs/testset_hard05_promptv2/prompt/refined_prompt.txt` 在 PE 阶段完成（18:53:36）后 35 秒被整篇手写替换（18:54:11）；`generation.json.prompt_sha256=17b9c608…` 与被改后的文件一致，与 `pe_result.json.compiled_prompt`（`c55965f6…`）不一致 |
| W2 | run 的身份就是目录名，复制目录即产生"两个实验" | `testset_hard05_fitgeo` 与 `testset_hard05_promptv2` 的 `geometry/stage.json`、`prompt/stage.json` 逐字节相同（md5 `fd932242…`、`3234112a…`），`completed_at_unix` 同为 1791715504 / 1791716016，`run.json` 的 started/finished 也相同；只有 `generation/stage.json` 不同。即 `fitgeo` 并未改几何，两者只差 prompt 文本 |
| W3 | 指纹里含易变绝对路径（原图路径、`run_dir`），改名或搬迁即全链路失效 | `fitgeo` 的 `request.json` 里 `run_dir` 仍指向旧名 `runs/testset_hard05_prompt`；`pictures/A|B` 的图被改名（`f2ce…jpg`→`A1.jpg`，内容 md5 未变）后，README 头条命令 `bash run.sh --verify` 直接 `WORKFLOW_FAILED: Prepared inputs are missing, changed, or stale` |
| W4 | 收尾无条件写"已全部校验" | 旧 `run.py` 结尾固定写入 `verification = 'Every output hash and every stage request validated'`；promptv2/fitgeo 在 `status: complete` 时该断言并不成立（`--verify` 实测失败） |
| W5 | stale 报错不可诊断 | 只有 `stage is stale or an artifact hash differs` 一句，不指出是设置、代码、输入哈希还是哪个产物变了；定位需手写脚本重算 request 并逐字段比对 |
| W6 | 崩溃后 manifest 永久停在 `running` | `runs/testset_hard05/run.json` 为 `status: running`，prompt 已完成而 `generation/` 不存在（10-11 18:06 被打断）；旧代码只在 Python 异常路径写 `failed` |
| W7 | 134 点布局的 body-18 眼/耳槽位与 OpenPose/DWPose 语义不一致，且测试无法发现 | 旧 `geometry.py` 的 `_BODY18_FROM_SMPLX137` 尾部为 `23,22,21,20`，即槽位 15/16 装的是 `L_Eye`/`R_Ear`，而 DWPose body-18 是 `R_Eye,R_Ear,L_Eye,L_Ear`。渲染因 `body_edges` 恰好自洽而未出错，但 `B_keypoints.npz` 的语义错位；旧 `tests/test_geometry.py` 只把同一张常量表重抄一遍断言 |
| W8 | 测试集含多人图，工作流没有主体选择机制 | `pairs/hard_01/A_source.png`（时装周照片）YOLO conf 0.5 下检出 3 人（0.915 / 0.892 / 0.850，最大框占画面 46.3%），旧代码直接 `RuntimeError: expected exactly one detected person`，批处理首对即失败 |
| W9 | 关键依赖跨到未入库的 vendor 目录，且无人校验 | `person_detection_confidence` 经环境变量 `SMPLESTX_DET_CONF` 生效，读取它的是 `add/tools/SMPLest-X/main/inference.py:100`；`/add/` 被根 `.gitignore` 忽略、git 跟踪 0 条，旧 `--check` 不验证该 hook 是否还在 |
| W10 | 子系统零版本控制，且不在仓库测试入口内 | `git ls-files workflow` = 0；`pytest.ini` 的 `testpaths = tests` 不含 `workflow/tests`，仓库层面"测试全绿"从不覆盖这条流水线 |
| W11 | 不是实验体系：无批量入口、无指标、无结果索引 | 测试集 7 对只跑过 2 对，5 个 run 目录里 4 个是同一对 `hard_05` 的手工变体，差异只编码在目录名里；`latest_run.json` 是全局单指针，任何一次运行都会覆盖；结果好坏只靠肉眼看图 |
| W12 | 骨架对齐用"人物框 min-scale 内切"，A/B 框长宽比相反时把姿态压得远小于源人物体格（W11 的指标上线后才被量化出来） | 5 对实测：`hard_05` 的 A 框长宽比 0.39、B 框 0.88，对齐尺度 0.410，请求骨架躯干仅 95.9px，而生成人物躯干 225.6px（2.35 倍错配）→ body PCK@0.2 = 0.056；其余四对 B 框都比 A 框窄，尺度 0.69–0.86，躯干比 0.97–1.09，PCK 0.944–1.000 |

## 二、本轮整改

| 编号 | 改动 | 对应问题 |
|---|---|---|
| R1 | PE 产物改为只读的 `prompt/pe_compiled_prompt.txt`；新增 `--prompt-file PATH`，由 `run.py:select_generation_prompt` 落成 `prompt/generation_prompt.txt` + `generation_prompt.json`（记录来源、来源哈希、生效哈希）。手工 prompt 从此是显式的哈希输入，重跑 PE 不再覆盖它 | W1 |
| R2 | 请求拆成 `identity`（设置、代码哈希、模型身份、输入内容哈希）与 `runtime`（绝对路径）两半；产物在 `stage.json` 里按相对 `run_dir` 记录，`stage.json` 自带 identity。改名、搬迁、换机不再使内容失效 | W3 |
| R3 | `pose_transfer/common.py:stage_reasons` 逐条说明失效原因：哪个设置字段变了、哪个代码文件变了、哪个产物在阶段写完后被改动（含记录哈希与磁盘哈希前缀） | W5 |
| R4 | 收尾对本轮涉及的每个阶段重跑 `stage_valid`，把实测结果写进 `manifest.verification.{status,reasons}` 并打印 `VERIFICATION validated|mismatch` | W4 |
| R5 | 新增 `report.py`：扫描全部 run，把"无写者的 running"标为 `abandoned`、旧 schema 标为 `legacy`，列出 prompt 来源、逐阶段耗时、评测指标，并给出测试集覆盖率与"哪些对还没跑" | W6、W2（可见化）、W11 |
| R6 | body-18 眼/耳槽位改为 `R_Eye,R_Ear,L_Eye,L_Ear` 并同步 `body_edges`（渲染像素不变，仅数组语义归位）；新增 `InstalledEstimatorLayoutTests`，直接解析安装版 SMPLest-X 的 `joints_name` 与 `flip_pairs` 来校验 body/feet/hands/face 各槽位语义与分块边界，不再重抄常量表 | W7 |
| R7 | 新增 `pose_transfer/geometry.py:choose_subject` 与 `--subject auto|largest|INDEX`（默认 `auto` 保持严格单人契约，索引基于"面积优先、再从左到右"的稳定排序）；B 侧增加一致性检查：估计器拟合出的关节质心必须落在所选人物框内，否则报错而不是把别人的姿态迁过来；`batch.sh` 在严格模式失败后显式回退 `--subject largest` 并在日志标注 | W8 |
| R8 | `--check` 增加 `ESTIMATOR_CONF_HOOK_OK` 断言：`main/inference.py` 必须仍读取 `SMPLESTX_DET_CONF`，否则报错说明该设置会静默失效 | W9 |
| R9 | `workflow/tests/conftest.py` + `pytest.ini` 的 `testpaths` 收编 `workflow/tests`，仓库根 `pytest workflow/tests -q` 可跑 | W10 |
| R10 | 新增 `--pair DIR`（自动取 `A_source.png`/`B_target.png` 并以目录名为 run 名）、`batch.sh`（逐对跑全测试集并评测，单对失败不中断）、`evaluate.py`（用同一估计器回估生成图骨架，与请求的骨架比 MPJPE / PCK，按 body / feet / face / 左右手分组，输出 `eval.json`、`final_keypoints.npz`、`eval_overlay.png`）；估计器调用抽到 `pose_transfer/estimator.py` 供几何与评测共用 | W11 |
| R11 | 新增 `--framing source_torso`：按"B 实测躯干长度 → A 框高 × 0.31 推出的源人物躯干"定标，替代宽度主导的内切缩放；默认仍是 `source_person`，既有行为与既有 run 不变。常数 0.31 由 5 对实测反推（颈-髋中心约占全身检测框高 0.31，与解剖常识一致），在该 5 对上把理想尺度命中到 ±4%，含 `hard_05` | W12 |
| R12 | 新增 `workflow/patches/`：把 vendor 估计器相对上游基线（`MotrixLab/SMPLest-X@fdebd887`）的全部本地改动（`SMPLest-X_local.diff`）与上游没有的入口脚本副本入库，并写明 workflow 只依赖其中的 `SMPLESTX_DET_CONF` hook 及恢复步骤 | W9 |

两处与原计划的偏离，说明如下：指标没有复用 `src/evaluation/joint_pilot_metrics.py`（那套面向 BFS 联合试点的数据与约定，复用会把 workflow 反向耦合到 `src/`），而是在 `evaluate.py` 里独立实现"回估生成图 → 与请求骨架比对"；`--verify` 的语义保持"代码哈希也在指纹内"，因此任何一次 workflow 代码改动都会让全部既有 run 报 `workflow code changed`，这是设计取舍而非缺陷，产物完好性看 `stage.json` 哈希或 `report.py`。

`run.py` 之外，`pose_transfer/common.py` 的记录 schema 升到 `single_person_pose_stage_v2`、manifest 升到 `single_person_pose_workflow_v2`。schema v1 的旧 run 是冻结证据，不再可 `--verify`；整改前已整树备份到 `/data/shangguanrz/pic-edit-archive/workflow_runs_backup_20261012/`（含 SHA256SUMS）。

## 三、尚未处理

- **多人 A 的语义仍未解决**：`--subject largest` 只是让流程能跑，选定主体后画面里其他人依旧存在，生成器可能改动他们；`evaluate.py` 只测姿态保真度，不测身份/服装/场景保持，也不检测"别人被改了"。多人图里评测还有第二重不确定：回估时估计器自己在生成图里挑人，`persons_detected > 1` 时无法保证它挑的就是当初选定的主体（`hard_01` 检出 3 人、`medium_01` 检出 2 人，指标虽好但要按这个前提读）。
- **`--framing source_torso` 的常数是在这 5 对上反推的**：0.31 与解剖常识一致、在 5 对上把理想尺度命中到 ±4%，但样本只有 5 对，且"检测框高等于身高"这个前提对半身/坐姿图不成立；它还没有和 `source_person` 在同一批图上做过完整 A/B（只补跑了 `hard_05`）。
- **评测指标未做交叉验证**：`evaluate.py` 用与被测图同一个估计器，估计器自身的偏差会同时进入分子分母；没有与人工标注或第二套检测器对照过。
- **W2 只做了可见化**：run 身份仍等于目录名，没有按 `pair + settings` 派生唯一 run 名，复制目录仍能造出两份"看起来独立"的记录（现在 `report.py` 能看出来）。
- **全测试集尚未在同一份代码状态下重跑**：九次运行分属三份 `pose_transfer/geometry.py` 状态（`6603a819…` 首轮批处理 5 对、`6a57ff88…` 两对多人图复跑、`5ac98986…` 两个 hard_05 变体），因此对它们执行 `--verify` 都会报 `workflow code changed`（产物完好）。逐对归属见 `workflow/README.md` 的"实况"一节。
- 仓库级 P0-1（git 三处分叉）、P0-2（根 `pytest` 收集期错误，实测 13 个，全部在根 `tests/`，与本轮无关：加 `workflow/tests` 前后同为 13）、P0-3（NVML 失配）不在本轮范围。

## 四、复核命令

```bash
cd /home/shangguanrz/project/pic-edit/workflow
PY=/home/shangguanrz/nihaochen/envs/qwen21/bin/python
GEOPY=$($PY -c 'import json;print(json.load(open("config.json"))["geometry_python"])')

bash run.sh --pair ../experiments/qwen-2.1-test/data/testset/pairs/hard_01 --resolution 768 \
     --subject largest                  # 多人图显式选主体

     --name hard_05_torso --framing source_torso   # 躯干定标 A/B，原 run 保留作对照
$GEOPY evaluate.py --run hard_05        # 只对单个 run 重算指标
$PY report.py                           # run 索引、覆盖率、指标、legacy/abandoned 标注
```
